# Uplift Narrator

Internal Woodruff Billing tool. Takes the summary document generated by the
Uplift Collator web app and produces a finished LAA enhancement narrative —
extracting the ticked criteria, attaching the correct citation to each one, and
polishing the result into flowing prose via a local LM Studio model.

Everything happens on this machine. LM Studio is local, so privileged client
material never leaves it — and that is enforced in code, not merely intended:
the narrator refuses any model address that is not loopback or the WSL host
gateway unless `UPLIFT_LMSTUDIO_ALLOW_REMOTE=1` is set deliberately.

Two front-ends:
- **GUI** (`narrate_gui.py`) — drop the summary on the window, click *Generate
  Narrative*, read the finished document. Uses the same dark theme as the
  `myToolbox` project so it can drop into that suite later.
- **CLI** (`narrate.py`) — same pipeline, scriptable. Useful for batch runs.

## What it reads: a `.docx` now, a PDF for older matters

The narrator reads the file the Uplift Collator web app downloads when you click
**Download Word Summary**. Since app v1.13 (7 August 2026) that is a **Word
document** — `Uplift_Justification-Smith 29964.docx`. Before then the same button
was called *Generate PDF Summary* and saved a PDF; **both formats are read, and
the PDF path is permanent**, because PDFs produced under the old button are
sitting in live matters and must keep working forever.

Which path runs is decided by the file's **own content**, not its name: a PDF
begins `%PDF`, a `.docx` is a zip beginning `PK`. A file renamed in transit
therefore still reads as what it actually is, and a file whose extension and
content disagree is reported as damage rather than guessed around.

The name is otherwise yours to change. Since v1.12 the download carries the
matter — so several cases in a morning no longer arrive as the same filename with
`(1)` and `(2)` after it — but rename it freely; the *content* is what matters.

**Why the format changed.** A PDF is a text layer with a line width, and jsPDF
wrapped anything wider than the column while marking the continuation in no way
at all. That single property caused the two worst defects this project has had (a
Stage 1 label that matched nothing and stopped every affected run, and a long
Case / Matter name silently truncated into the narrative), and cost five review
rounds of hardening in `extract.py`. In a `.docx` the contract is **paragraph
equality**: every heading, detail line, bullet and sentinel is exactly one Word
paragraph, and python-docx returns each one whole however long it is. Nothing
wraps, so `extract_docx.py` has no rejoining logic at all — and must never grow
any. Text a solicitor *pastes* into an explanation cannot imitate structure
either: its newlines are encoded inside that explanation's own paragraph, so no
line of it can ever equal a heading paragraph.

If nothing can be recovered from either format, the run **stops at the input
document** and says why in plain English — it does not build an empty narrative
and then report it as a citation failure, which is what it used to do.

## Legacy PDFs

Everything in this section is about the **PDF path** — files produced before
v1.13, which the narrator will keep reading indefinitely. None of it can happen
to a `.docx`, which is why the format changed.

### It cannot read a Print / Save-as-PDF file

The narrator cannot read a PDF made by the browser's own Print / Save-as-PDF,
because printing captures the on-screen page, which has none of the section
structure the narrator parses. The only PDFs it reads are the ones the app itself
generated, from the button as it was named before v1.13.

### The file must still have its text layer

A correctly-generated Collator PDF can still arrive unreadable if something
stripped its text **after** the app saved it. The give-away is that you cannot
select any text in it. This is not a mistake anyone made in the app.

There are two ways it happens, they look identical on screen, and they need
different explanations:

| | What happened | Fingerprint |
|---|---|---|
| **Rasterised** | The page became a picture of itself | no text, one full-page image |
| **Outlined** | Each letter became a drawing of its own shape — still crisp at any zoom | no text, **no** images, thousands of vector objects |

`--debug` tells them apart, and names the culprit from the PDF's own
`producer` metadata. **The app's own PDFs always say `jsPDF`**, carry text, and
contain no images at all — so anything else is something that touched the file
later. `PRODUCER_NOTES` in `extract.py` turns the common ones into plain
English; add to it when a new one turns up.

That test still holds *of PDFs*, and it has become a dating test as well: the app
has not produced a PDF since v1.13 (7 August 2026), so any **new** file is a
`.docx`. The equivalent forensics there live in `docProps/core.xml` — the
Collator writes itself in as the creator ("Uplift Collator v1.13"), and Word
records whoever re-saved the document in `lastModifiedBy`, which the PDF format
had no counterpart for. See *Troubleshooting* → `--debug`.

Seen in practice on 1 August 2026 — a correct v1.10 PDF, `raw_chars: 1`,
`images: 0`, `vector_objects: 6099`, producer **`Aspose.Pdf for .NET 11.7.0`**.
Aspose is a library that runs inside other software (case-management systems,
portal uploads, e-bundling tools, mail gateways), so a system did this in
transit — meaning it will do it to every future case until it is found.

**The fix is always to get the original file**, straight from the browser's
Downloads folder before it was filed, uploaded or forwarded. The narrator
deliberately does **not** OCR: on an audited claim a mis-read page count or
percentage is worse than no narrative at all — the same reasoning that picked
the default model (see *Choosing a model*). If the original is genuinely gone,
re-enter the answers in the web app — which will now hand you a `.docx` rather
than another PDF, and one that cannot suffer this at all.

### If you OCR one yourself, expect damaged labels

Putting a flattened PDF through Acrobat's OCR does get the words back, but not
faithfully. A file recovered that way on 4 August 2026 returned `Exceptional
weight {docs/issues) (as per Stage 1)` — an opening bracket read as a brace —
and `documentation volume/ number`, with the space before the slash lost.

A ticked item whose label matches nothing in `content-data.js` **stops the
run** — that rule is not PDF-specific, it guards both formats — and the report
names the character that differs:

```
narrate: 2 ticked items could not be matched to a criterion in content-data.js.

  stage2 — read:    'Exceptional weight {docs/issues) (as per Stage 1)'
           nearest: 'Exceptional weight (docs/issues) (as per Stage 1)'
           first difference at character 20: read '{', expected '('
```

It stops rather than quietly repairing the bracket, because the explanation
underneath a mangled label came off the same damaged text layer. Correcting
what you can see would leave prose that is just as wrong and no longer looks
it. Before this existed the item was skipped with a line on stderr, so a factor
the solicitor claimed simply disappeared — and a narrative missing an argument
reads exactly like one that never made it.

The report is safe to paste anywhere: a read label is shown only where it is
demonstrably a damaged copy of a known one, and the explanation is never
included. A bulleted line too unlike any criterion is reported by length alone,
because it may be case text rather than a label at all.

Everything recovered is written to `narrative-input.json` *before* the stop, so
the way forward is to correct each `label` in that file and re-run without
going near the damaged document again:

```bash
python narrate.py --from-json ".../narrative-input.json"
```

Corrected labels are re-resolved against `content-data.js`, so one is accepted
only if it now matches **exactly**; near enough does not pass. Anything still
unmatched stops the run again.

**Avoiding the OCR entirely is still better.** Paste the recovered text into
the web app, proofread it there against the rendered page, and download a fresh
summary. That repairs the labels for free, puts the proofreading at the point
where you are already reading the words — which has to happen somewhere either
way — and the file you get back is a `.docx`, so the whole class of damage
described in this section cannot recur on it.

## What it produces

For an input `case.docx` (or a legacy `case.pdf`), both front-ends write a folder
`case-narrative/` next to the input file:

- **`narrative-polished-<matter>.docx`** — the finished narrative as a Word
  document, named for the case (`narrative-polished-Smith 29964.docx`), so the
  file says which matter it belongs to once it is attached to an email.
  **This is the one you send.** It is a *fragment*, not a standalone document:
  it is written to be pasted straight into the CCMS bill narrative as its final
  section, "Claim For Additional General Enhancement". It therefore has no title
  block, no page numbers and no footer — all of which would be wrong inside a
  longer document — and it uses the bill narrative's own typography (Arial Nova
  Cond Light 12pt, single spaced, A4, 0.5in margins) so the join is invisible.

  The layout: bold section heading, bold category sub-headings, and one bullet
  per criterion with the criterion name bolded as a run-in lead and the
  solicitor's evidence following on the same line. The criteria are bulleted
  because an assessor works down them one at a time and strikes any that are
  disallowed. Headings are bold only — underline conventionally signals a
  citation in legal drafting, so using it for headings competes with the
  authorities that are the point of this section.
- **`narrative-polished-<matter>.md`** — the same narrative as plain text, named
  to match the .docx. The audit and
  diff copy, and what the GUI's *Polished Narrative* tab shows. Identical in
  substance to the .docx; the conversion refuses to write a Word file that does
  not carry exactly the same citations, in the same counts (see below).
- **`citation-check.txt`** — proof that nothing was lost in the polish step: a
  deterministic citation and placeholder check, plus a second-opinion review
  from the model. Ends in an overall verdict — `SAFE TO REVIEW` or `NEEDS
  REVISION` — that reflects *both* checks. A discrepancy found by either one
  fails the run, and the CLI exits non-zero so a batch loop cannot mistake a
  flagged narrative for a clean one.

  It may also carry a **Number agreement** note. When a claim rests on a single
  factor the framing sentences are written in the singular, because "These
  factors, individually and/or cumulatively" applied to one factor asserts
  something that cannot be true — in the sentence carrying the whole
  justification. The skeleton gets this right from the count, but the polish
  step rewrites those sentences, so this reports the model putting the plural
  back. It is deliberately a **warning and does not fail the run**: bad grammar
  is an embarrassment, not a false statement to the LAA, and failing over it
  would train you to ignore a red verdict.
- **`narrative.md`** — the fully-cited skeleton the polish step worked from.
  The audit trail, and the fallback if LM Studio is unavailable.
- **`narrative-prompt.txt`** — the exact instruction sent to the model. Kept as
  an audit record if an assessment is ever challenged, and still paste-ready.
- **`narrative-input.json`** — the recovered form data, in the same shape as the
  in-app `formData`. Useful for debugging extraction or re-running the skeleton.

### Why the Word file is checked separately

`citation-check.txt` certifies the *Markdown*. The Word file is what actually
gets sent, so if the conversion lost a citation the audit record would attest to
a document nobody sent.

That is not hypothetical. The model puts citations *in its headings* — `##
Threshold Test (Qualifying for Enhancement - Spec Para 6.13 / CAG Section 12.4)`
— so deleting those headings to make the section read well inside the bill
narrative, which is the obvious thing to do by hand, silently takes two
certified authorities with it. The converter therefore **demotes** headings to
bold sub-headings rather than deleting them, and drops only headings that both
are pure scaffolding (`Introduction`, `Conclusion`) *and* contain no citation.

After building the document it re-runs the citation extractor over the finished
Word file and refuses to save it unless the citations match the Markdown
exactly, in the same counts. If that ever fails, the run says so and exits
non-zero; the `narrative-polished-<matter>.md` is unaffected and can be used
instead.

Both polished files fall back to the bare `narrative-polished.docx` /
`narrative-polished.md` when the input carries no usable matter name — a file
called `narrative-polished-unknown.docx` would be worse than one with no suffix
at all. `citation-check.txt` keeps its fixed name: it certifies the run rather
than being something you send on.

**The polished narrative still needs a human review pass before it goes to the
LAA.** The checks tell you nothing was dropped; they cannot tell you the
submission is right.

## Quick start

```bash
cd _narrator
./_setup.sh                  # one-time: creates conda env 'uplift-narrate'
./_narrator.sh                     # launches the GUI
./_narrator.sh path/to/case.docx   # launches the GUI with that summary pre-loaded
```

Windows: `_setup.bat` and `_Generate_Uplift_Narrative.bat` (double-click, or drag the summary onto `_Generate_Uplift_Narrative.bat`).

For the CLI:

```bash
conda activate uplift-narrate
python narrate.py path/to/case.docx --polish [--model NAME] [--no-verify]
```

A legacy `case.pdf` is passed exactly the same way — there is no flag to set and
nothing to tell the tool. It looks at the file.

Without `--polish` the CLI stops at the skeleton and the paste-ready prompt.
The GUI always attempts the polish step, and falls back to the skeleton if
LM Studio cannot be reached.

To resume a run that stopped on an unmatched label, give the corrected
`narrative-input.json` instead of the summary — the two are alternatives, so pass
one or the other:

```bash
python narrate.py --from-json ".../narrative-input.json" --polish
```

Exit codes: `2` bad arguments or an unreadable file, `4` nothing extractable in
the input document, `5` a ticked item matched no criterion.

Batch:

```bash
for f in /path/to/summaries/*.docx; do python narrate.py "$f" --polish; done
```

Add `*.pdf` to the glob if the folder also holds summaries from before v1.13.

## Choosing a model

The picker lists everything downloaded in LM Studio and marks what is already
loaded. **Auto** stays on whatever currently occupies VRAM, or falls back to
`gemma-4-26b-a4b-qat`.

That default is not a guess. In the LeapForward bake-off
(`~/coding/LeapForward/docs/model_comparison.md`, 17 May 2026) Gemma-4-26b-a4b
beat gpt-oss-20b on *safety* for audited Legal Aid work: it never invented work
that had not happened and never duplicated a quantity. On an LAA submission,
plausible-but-wrong is the worst failure class — the same reason it leads here.
The QAT build is pinned ahead of the plain one, which spills VRAM on a 16GB card.

### Sharing LM Studio with another application

Two models this size cannot share a 16GB card, so switching model means
unloading whatever is there — which may belong to another application
(LeapForward, say) that is mid-run. The narrator never does that silently:

- **Auto never swaps.** It deliberately stays on whatever already occupies
  VRAM, so the default path cannot disturb anything.
- **An explicit pick that differs from the loaded model asks first**, naming
  what would be unloaded and the context length it was loaded at. Cancel and
  nothing is touched. Consent is recorded as *those specific model ids*, and
  the state is re-read immediately before acting — so if a different model has
  appeared in the meantime it is never evicted on that consent. The narrator
  never runs `unload --all`.
- **The CLI refuses by default** and exits 3, telling you to pass
  `--force-swap` or drop `--model`. Batch runs therefore stay safe and
  non-interactive.

Sharing the *same* model is fine — LM Studio queues requests, so a run behind
someone else's simply waits its turn.

**Two gaps remain, and are accepted rather than fixed.** A model that appears
in the last fraction of a second — between the final state check and the
`lms` command — can still be evicted; closing that properly needs a lock
between the two applications, which LM Studio does not offer. And when
LM Studio's `/api/v0` endpoint is unavailable the loaded state is unknown, so
the narrator makes the request and lets LM Studio's own just-in-time loading
decide, which may evict something. Both are narrow; neither is silent about
what it did.

If another application loaded the model at a smaller context length than the
narrator would have chosen, the narrator inherits it rather than reloading. A
long narrative can then overflow; the confirm dialog shows the loaded context
so this is visible before it bites.

## Editing the prompts

**Edit Prompts** opens your own copy of the system prompt and user template in
Notepad++ (or Notepad). Saved edits apply to every future case until you press
**Restore Defaults**. The window shows *Prompts: default* or *Prompts:
customised* so a customised prompt is never a surprise.

Shipped defaults live in `prompts/` and are never modified. Your edits live in
`prompts/custom/`, which **is committed to the repo on purpose** — a prompt
tuned on Mutant should reach Darwin. Two machines quietly running different
prompts is the kind of divergence that produces a confusing result months later
with no way to explain it.

Editing is safe to expose because it cannot disable the safety net: the citation
check reads the skeleton, not the prompt. Delete "preserve every citation" from
`system.md` and the consequence is still caught.

## How it works

1. **Extract** (`extract.py`, dispatching to `extract_docx.py`). `extract.py` looks
   at the file's first bytes and sends it down one of two paths.

   *The `.docx` path* (`extract_docx.py`, python-docx) walks the document's
   paragraphs and matches them **whole**: a section heading is a paragraph whose
   entire text equals CASE DETAILS, PANEL MEMBERSHIP, STAGE 1…, a detail is one
   reading `Label:  Value`, a ticked criterion is one starting `•`. No regex over
   a wrapped text layer, and so no rejoining logic — see the format note above.

   *The PDF path* (`pdfplumber`, frozen and permanent for live matters) opens the
   PDF, slices it into sections by the UPPERCASE headers the retired
   `generatePdfSummary` produced, then regexes out each ticked criterion's label,
   category title, and "Explanation: …" block.

   Everything **semantic** is shared rather than written twice: the label →
   `QUESTION_BLOCKS` key lookup, the section-prefix guard that stops a Stage 2
   label being read as a panel membership, the unrecognised-label records, and
   the meaning of every field. The two paths differ only in how they get text off
   the page.
2. **Skeleton** (`skeleton.py`). For each ticked key, looks up the matching entry
   in `NARRATIVE_TEMPLATES` (defined in `../content-data.js` — the single source
   of truth) and substitutes the live values: `{UPLIFT_PERCENT}`,
   `{ITEM_OF_WORK}`, `{FEE_EARNER_NAME}`, `{PANEL_NAME}`, and
   `{USER_EXPLANATION}` (the solicitor's verbatim text as a blockquote).
   Bracketed placeholders such as `[SPECIFY ARGUMENT]` are intentionally
   preserved — they cue the polish step to draw on the explanation that follows.
3. **Prompts** (`prompts.py` + `prompts/`). Resolves custom override or shipped
   default, then substitutes case context and the skeleton.
4. **Polish** (`polish.py` + `lmstudio.py`). Loads the chosen model and rewrites
   the skeleton as flowing prose, filling the bracketed placeholders from the
   explanations.
5. **Completion check** (`lmstudio.py`). A generation that was cancelled,
   truncated at the token limit, cut short, or missing frames is discarded
   rather than saved. A narrative truncated after its headings and citations
   would otherwise pass the next step and be filed as finished work.
6. **Check** (`checks.py`). Regexes every `Spec Para` / `CAG` / `CPR` citation
   out of the skeleton and confirms each survived, flags any citation the model
   *added*, and flags any placeholder left unfilled. Deliberately not an LLM —
   this question has an exact answer.
7. **Second opinion** (`prompts/verification.md`). A separate model call that
   compares skeleton against polished output for facts quietly *altered* rather
   than deleted — the failure a regex cannot see. If it fails, the narrative is
   still kept.

`content-data.js` is the canonical home of the questionnaire and templates.
`templates.py` parses it at runtime via `json5`, so any future edit to the web
app's templates flows through automatically.

The GUI is a PyQt6 front-end built on the **Worker / Card / Window / Manager**
pattern from `~/coding/myToolbox` so the tool can later drop into that suite
(`NarrateManager.open_window()` is the integration entry point). The LM Studio
mechanics are inherited from `~/coding/LeapForward` (`leapforward_app/llm.py`),
which learned them against the same machine and the same class of work.

## Requirements

Python 3.10+ and conda. **LM Studio** with its local server running (Developer
tab → server on) for the polish step; everything up to the skeleton works
without it.

Dependencies (installed by `_setup.sh` / `_setup.bat`):
- `python-docx` — reads the `.docx` summary **and** writes the Word narrative
- `pdfplumber` — text extraction from legacy PDF summaries
- `json5` — parses the JS-style content-data.js cleanly
- `PyQt6` — GUI front-end

The LM Studio client is stdlib-only (`urllib`), so adding it required no new
dependency and no re-run of `_setup`.

**If you already have the `uplift-narrate` env from before 1 August 2026**, it
predates `python-docx` and the GUI will stop at
`ModuleNotFoundError: No module named 'docx'`. Re-run `_setup` — both scripts
update an existing environment in place rather than only creating a new one.

**Windows and WSL have separate conda environments that share the name
`uplift-narrate`.** They are two independent installations, so installing a
package on one side does nothing for the other. Run `_setup` on whichever side
you actually launch the tool from — `_setup.bat` for
`_Generate_Uplift_Narrative.bat`, `_setup.sh` for `./_narrator.sh`. If you use
both, run both.

The narrative this tool produces is the last section of the firm's CCMS bill
narrative. The style authority for that document is **not** this repository —
it is `~/coding/LLM-benchmarking/docs/real-format-notes.md`, which is the master

that is where the Word file's heading, typography and layout come from.

Any deliberate divergence from that document belongs here, in writing, with the
reason. There is currently one thing to reconcile: §B7 names this project's
source folder as `narrative`, which is now `_narrator`.

## Tests

```bash
conda activate uplift-narrate
python -m unittest discover -s _narrator/tests -v
```

378 tests, verified under both WSL and Windows Python on 7 August 2026. The suite
never touches the network — it passes with LM Studio closed. The citation cases
are generated from `content-data.js` rather than chosen by hand: an earlier suite
passed 20 tests while the checker was silently fail-open on `CAG Section 12.5 &
12.9`, because no test used the citation forms that actually occur in the
templates.

**When a label or the generator changes, rebuild the `.docx` fixtures:**

```bash
node _narrator/tests/build_docx_fixture.js
```

It builds `sample.docx`, `deemed.docx` and `nasty.docx` with the **real**
generator — the same `docx-summary.js` the browser loads — reading labels,
category titles and the version constant live out of `content-data.js`. A
hand-copied label in a fixture goes stale the day the wording changes, and the
fixture then silently tests a document the app can no longer produce. Output is
deterministic (fixed dates and zip timestamps), so a fixture diff in git always
means the generator or the data changed, never the clock.

`nasty.docx` is the adversarial one, and worth knowing about: an explanation
carrying a fake DISCLAIMER heading, a fake EVIDENCE ON FILE block claiming
confirmation, a real Stage 1 label on its own pasted line, bullet characters and
a control character. The paragraph contract must keep all of it inert inside the
explanation.

`measure_pdf_labels.js` used to sit beside these, measuring whether a label would
wrap in the PDF. It was **deleted on 7 August 2026**: there is no jsPDF and
nothing wraps, so there is nothing to measure. Its whole defect class went with
it. The PDF *fixtures* and every PDF extraction test stay — that path now serves
live legacy matters.

A real-Word acceptance check was also run once, by COM automation on 7 August
2026: Word opened the generated document without offering to repair it,
extraction was identical after a Word re-save, and the `docProps` creator "Uplift
Collator v1.13" survived the round trip while `lastModifiedBy` recorded who
re-saved it. That is manual, not part of the suite.

## Troubleshooting

**"Nothing was extracted from this document"** — the run stopped at the input and
the message names the likely cause and the fix. Almost always the file did not
come from the app's **Download Word Summary** button (or, for an older matter,
the *Generate PDF Summary* button that preceded it). See the sections above.

**"Could not reach LM Studio"** — open LM Studio → Developer tab → turn the
server on. Under WSL the server is reached on the WSL2 gateway IP, not
`localhost`; this is detected automatically and re-detected each run, because
the gateway IP changes across reboots. Override with `UPLIFT_LMSTUDIO_URL` if
you run it on a non-default port.

**The model returns an empty narrative** — think-by-default families (Gemma 4,
Qwen 3.5+) spend their whole token budget reasoning unless switched off. LM
Studio only honours `reasoning_effort: "none"` for this; the template-level
flags (`enable_thinking`, `chat_template_kwargs`) are ignored. Add the model's
name to `THINKING_OFF_PATTERNS` in `lmstudio.py`.

**`NEEDS REVISION` in the citation check** — read `citation-check.txt`. A
*dropped* citation is an assertion to the LAA that has lost its authority; an
*added* one may be an invented authority. Re-run, or try a different model.

**Empty narrative on a real case file** — run the structure-only diagnostic
first. It works on either format and picks the right one itself:

```bash
python narrate.py --debug "/path/to/case.docx"
```

Neither version prints client text, so the output is GDPR-safe to share when
triaging. Both report per-section match flags and bullet/explanation counts, and
a `"matched": false` entry pinpoints the section that was not found.

For a **`.docx`** it also reports the document's own identity: `creator` (the
Collator writes "Uplift Collator v1.13"), `last_modified_by` (whoever re-saved it
in Word), `created` and `modified`, and `rewritten_after_seconds` between the
two. `made_by_the_app: false` beside real text means something rebuilt the file
after download. If the document will not open as a Word package at all, the
diagnostic says which way it failed — `not_a_zip` or `not_a_word_package`.

For a legacy **PDF** it reports page/char counts, image and vector-object counts,
and the `producer`/`creator` metadata described earlier; `header_matches: 0` or
`footer_matches: 0` means the PDF was produced by an older app version with
different boilerplate.

**"narrate: unknown panel/criterion label"** — the summary was generated against
an older version of `content-data.js` whose labels have since changed. Either
regenerate it from the current web app, or restore the older `content-data.js`
long enough to extract. (`LEGACY_LABEL_ALIASES` already covers the wording used
before the 4 August 2026 redesign.)

**Section-header detection misses something** — the headings are an extraction
contract shared by both formats, carried over into the `.docx` word for word. For
a `.docx`, update `SECTION_HEADINGS` in `extract_docx.py` to match
`docx-summary.js`. For a legacy PDF, update `SECTION_PATTERNS` in `extract.py` —
though that generator is retired, so the only reason to touch it is a file that
was always read wrongly.
